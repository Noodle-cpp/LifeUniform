## Life Uniform — архитектурный документ и ADR (MVP)

Дата: 2026-08-11
Язык: RU

### 1. Цели MVP
1. Интернет-магазин мед. одежды `Life Uniform` с UX уровня референса `wear-plus.ru` (адаптивный каталог, карточки, корзина, оформление заказа).
2. Личный кабинет: регистрация/вход/роли, профиль, история заказов.
3. Функции MVP:
   - избранное
   - промокоды
   - заказ без интеграции реального платежного провайдера (QR/SБП — только как заглушка до выбора провайдера)
4. Админка (минимальная): добавление/редактирование товаров и категорий, загрузка изображений, управление заказами (в т.ч. ручной отметкой “Оплачено” для MVP).
5. 1С: двусторонний обмен “как контракты” (интерфейсы, схемы сообщений/файлов, фоновые синхронизации) — реализацию обмена отложить, но архитектуру подготовить.

### 2. Ограничения по “бесплатным технологиям”
- UI: Bootstrap 5 (локальные файлы в `wwwroot/lib` через LibMan или статические поставки).
- БД: PostgreSQL.
- ORM: EF Core 10.
- Валидация: FluentValidation.
- Маппинг: AutoMapper.
- Картинки: обработка превью + webp (в архитектуре предусмотрено). Сейчас пакет ImageSharp временно не подключён из-за требования лицензии Six Labors в этой среде; UI использует placeholder, а точки расширения под обработку/хранение остаются.
- Тесты: xUnit + FluentAssertions. Моки: Moq.
- Тест-инфраструктура: без обязательного Docker в MVP. Для интеграционных тестов допустимо SQLite (см. ADR по тестам).

### 3. Архитектурный стиль (ADR-0001)
**Решение:** Clean Architecture со слоями:

`Domain` → `Application` → `Infrastructure` → `Web (Razor Pages)`

CQRS в `Application`:
- `Commands/Queries`
- `Handlers`
- `Validation` через FluentValidation

**Почему:** хорошая тестируемость (unit + integration), понятные границы, соответствие действующим правилам в репозитории.

**Где какие типы:**
- `Domain`:
  - сущности/ValueObjects (например, `Product`, `Category`, `Order`, `Money`)
  - доменные исключения
  - интерфейсы репозиториев и сервисов, которые нужны бизнесу
- `Application`:
  - DTO для запросов/ответов
  - команды/запросы и обработчики
  - бизнес-валидаторы (FluentValidation)
  - AutoMapper профили (Mapping: DTO ↔ модели)
  - интерфейсы внешних адаптеров (например, `IErpSync`, `IImageStorage`, `IPaymentFacade`)
- `Infrastructure`:
  - EF Core DbContext/конфигурации
  - реализации репозиториев
  - Identity store (если объединяем в одном DbContext)
  - реализации `ImageSharp` пайплайна и `IImageStorage` (Disk сейчас, MinIO позже)
  - реализации ERP адаптера (stub сейчас, контракт готов)
- `Web`:
  - Razor Pages (PageModel) — “тонкие” контроллеры без бизнес-логики
  - авторизация `[Authorize]` и роли
  - UI-маппинг моделей (через Application DTO)

### 4. Привязка к Razor Pages (ADR-0002)
**Решение:** Web слой использует `IMediator`/`Send` для выполнения команд/запросов.

- PageModel принимает `DTO`/формы
- вызывает `await _mediator.Send(...)`
- возвращает представления/редиректы

### 5. EF Core + Postgres (ADR-0003)
**Решение:**
- Основная БД — PostgreSQL.
- Сущности картируются EF Core Fluent API.
- Миграции — на разработке и в CI.

**Замечания:**
- Для read-only запросов используем `.AsNoTracking()`.
- Для коллекций/агрегаций аккуратно управляем `.Include()` чтобы избежать N+1.

### 6. Identity (ADR-0004)
**Решение:** ASP.NET Core Identity для:
- регистрация/логин
- роли
- профиль (минимально: имя/фамилия/телефон/город — по необходимости)

**Роли в MVP:**
- `Customer` — обычный пользователь
- `Admin` — управление каталогом и заказами

Публичные страницы доступны всем.
Админка ограничена ролью `Admin`.
Заказы/избранное/профиль — только `Customer` (для админа — тоже доступно).

### 7. 1С двусторонний обмен (ADR-0005)
В MVP реальный обмен может быть отложен, но контракт должен быть предусмотрен.

**Решение:**
- В `Application` вводим интерфейс(ы) обмена:
  - `IErpCatalogImporter` (Inbound: 1С → магазин)
  - `IErpOrderExporter` (Outbound: магазин → 1С)
  - Опционально единый `IErpSyncService` с “планом” синхронизации
- В `Infrastructure` создаём адаптеры:
  - `StubErp*` для MVP (ничего не делает кроме логов/симуляции)
  - будущие реализации:
    - `HttpErpClient` (если будет доступен HTTP-сервис со стороны 1С/шлюза)
    - `FileErpClient` (XML/JSON/CommerceML файлы по папкам/FTP)

**Почему так:**
- “http сервис не понятен”: 1С может быть интегрирована по-разному (HTTP/файлы/очереди). Интерфейсы позволяют не “вплести” транспорт в доменную часть.

**Что синхронизируем на уровне контракта:**
- Каталог: категории, товары, SKU/цены (в MVP — розница, без оптовых прайсов).
- Заказы: позиции, адрес доставки, суммы, статусы (Pending → Paid → Shipped/Cancelled).

### 8. Кэш (ADR-0006)
**Решение:** `IMemoryCache` для:
- главной страницы
- категорий
- популярных товаров

**Инвалидация:**
- при изменениях в админке (товары/цены/наличие) соответствующие ключи удаляются.
- TTL базовый (например, 10-30 минут) с возможностью уточнения позже.

### 9. Изображения (ADR-0007)
**Решение:**
- Публичные карточки используют:
  - превью (несколько размеров)
  - webp
- Обработка — план `ImageSharp` (или альтернативная реализация после решения вопроса лицензии).
- Хранилище медиа реализуем интерфейсом:
  - `IImageStorage` (dev: диск)
  - `IMinIoImageStorage` — подготовить для будущего запуска

**Пайплайн:**
1. Загруженный оригинал сохраняется в хранилище.
2. Генерируются превью и webp (например, 400px wide, 800px wide + webp).
3. В БД хранится метадата:
   - исходный файл
   - список производных размеров (пути/имена/хэши)

### 10. QR платеж (ADR-0008)
**Решение для MVP:** QR (СБП) реализуется как заглушка без реального провайдера:
- при создании заказа генерируем “payment token”
- показываем QR на страницу оплаты (QR ведёт на страницу “Подтвердите оплату” либо на UI-эмуляцию)
- статус заказа в MVP:
  - `PendingPayment`
  - `Paid` — выставляет `Admin` вручную (или через будущий callback провайдера)

**Почему:**
- Реальная интеграция СБП требует провайдера/контрагентов и обычно платных/лицензионных компонент. Чтобы не “заблокировать” разработку, MVP сначала закрывает витрину и процесс заказа.

### 11. Промокоды и скидка (ADR-0009)
**Решение:** сущность `PromotionCode` + правило применения:
- тип: процент/фикс
- ограничение: срок действия, минимальная сумма (опционально)
- применение: на уровне корзины/создания заказа

Опционально: “цена и цена со скидкой” — хранится и/или вычисляется при выдаче карточки товара.

### 12. Каталог как MVP (ADR-0010)
**Решение по модели:**
- Категории: без аксессуаров (MVP).
- Товары:
  - `Gender` не обязательно как enum в UI (но можно для группировки)
  - атрибуты для карточек: название, описание, состав/материал, размеры (если нужно), варианты цвета

Если “SKU = цвет+размер” — делаем SKU таблицу и остаток на SKU, но в MVP можно начать с уровня “товар” и расширить позже.

### 13. Корзина/избранное (ADR-0011)
**Решение:**
- Корзина:
  - MVP: сессия для гостей (или cookie-based) + мерж после логина (по необходимости).
- Избранное:
  - таблица `UserFavoriteProducts`
  - доступ по Identity user id.

### 14. Тестовая стратегия (ADR-0012)
**Решение:**
1. Unit tests:
   - проверяем handlers команд/запросов
   - моки внешних адаптеров (Moq)
2. Integration tests:
   - используем `Microsoft.AspNetCore.Mvc.Testing`
   - приоритет: проверить ключевые Razor Pages сценарии (каталог/карточка/корзина/создание заказа)

**DB в integration tests без Docker:**
- допускаем SQLite in-memory (EF Core провайдер) для быстрых тестов.
- Postgres проверяется отдельным прогоном разработки/CI (не обязательно в рамках каждого локального теста).

### 15. Папки/проекты solution (ADR-0013)
Рекомендованная структура solution:

- `LifeUniform.Domain`
- `LifeUniform.Application`
- `LifeUniform.Infrastructure`
- `LifeUniform.Web` (Razor Pages)
- `LifeUniform.Tests.Unit`
- `LifeUniform.Tests.Integration`

`LifeUniform.Web` зависит от `Application`, а `Application` — от `Domain`.
`Infrastructure` зависит от `Domain` и `Application`, и внедряет реализации интерфейсов в DI контейнер.

### 16. Нефункциональные требования (кратко)
- Адаптивный UI (mobile-first) + страницы соответствуют общему layout (Bootstrap grid).
- Безопасность: анти-форджери токены в формах, авторизация Razor pages по ролям.
- Observability позже: логирование запросов/ошибок, correlation id (опционально в MVP).
